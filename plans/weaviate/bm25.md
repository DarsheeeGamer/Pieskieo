## Overview

BM25 (Best Matching 25) is a ranking function used by search engines to estimate the relevance of documents to a given search query. It's an essential component of Weaviate's hybrid search feature. Unlike exact text matches (`LIKE` or `=`), BM25 accounts for term frequency, document length, and inverse document frequency (how rare the term is across all documents).

## Target Functionality

### 1. Tokenization and Normalization
- Split text into terms (words).
- Lowercase normalization.
- Stopword removal (e.g., "the", "a", "is").
- Stemming/Lemmatization (optional but recommended for better recall).

### 2. Inverted Index Construction
- Map each term to a list of `(RowId, TermFrequency)`.
- Track total number of documents ($N$) and average document length ($avgdl$).

### 3. BM25 Scoring Algorithm
$$ \text{score}(D, Q) = \sum_{i=1}^{n} \text{IDF}(q_i) \cdot \frac{f(q_i, D) \cdot (k_1 + 1)}{f(q_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{avgdl}\right)} $$
- $q_i$: query term
- $D$: Document
- $f(q_i, D)$: Term frequency in the document
- $|D|$: Length of the document
- $avgdl$: Average document length across the collection
- $k_1$: Term frequency saturation parameter (default 1.2)
- $b$: Length normalization parameter (default 0.75)
- $\text{IDF}(q_i) = \ln\left(\frac{N - n(q_i) + 0.5}{n(q_i) + 0.5} + 1\right)$ where $n(q_i)$ is the number of docs containing the term.

## Implementation Plan

### Phase 1: Text Processing Pipeline

We need a configurable pipeline to process text fields before indexing.

```rust
// crates/pieskieo-core/src/search/analyzer.rs

pub trait Analyzer {
    fn analyze(&self, text: &str) -> Vec<String>;
}

pub struct StandardAnalyzer {
    pub lowercase: bool,
    pub remove_stopwords: bool,
    pub language: String, // "en", "es", etc.
}

impl Analyzer for StandardAnalyzer {
    fn analyze(&self, text: &str) -> Vec<String> {
        let mut tokens = Vec::new();
        // 1. Lowercase (if configured)
        let text = if self.lowercase { text.to_lowercase() } else { text.to_string() };

        // 2. Tokenize (split on whitespace and punctuation)
        for token in text.split_whitespace() {
            let clean_token = token.trim_matches(|c: char| !c.is_alphanumeric());
            if !clean_token.is_empty() {
                // 3. Stopword removal
                if self.remove_stopwords && is_stopword(clean_token, &self.language) {
                    continue;
                }
                tokens.push(clean_token.to_string());
            }
        }
        tokens
    }
}
```

### Phase 2: BM25 Inverted Index

This structure will be maintained alongside our Vector and GIN indexes.

```rust
// crates/pieskieo-core/src/index/bm25.rs

pub struct BM25Index {
    // Term -> Posting List
    pub inverted_index: BTreeMap<String, Vec<Posting>>,

    // Document statistics for scoring
    pub doc_lengths: HashMap<RowId, usize>, // |D|
    pub total_docs: usize,                  // N
    pub total_length: usize,                // sum(|D|)

    // Tuning parameters
    pub k1: f32,
    pub b: f32,
}

#[derive(Clone, Debug)]
pub struct Posting {
    pub row_id: RowId,
    pub frequency: usize, // f(q_i, D)
}

impl BM25Index {
    pub fn insert(&mut self, row_id: RowId, text: &str, analyzer: &dyn Analyzer) {
        let tokens = analyzer.analyze(text);
        let doc_length = tokens.len();

        self.doc_lengths.insert(row_id, doc_length);
        self.total_docs += 1;
        self.total_length += doc_length;

        let mut term_counts: HashMap<String, usize> = HashMap::new();
        for token in tokens {
            *term_counts.entry(token).or_insert(0) += 1;
        }

        for (term, freq) in term_counts {
            self.inverted_index
                .entry(term)
                .or_insert_with(Vec::new)
                .push(Posting { row_id, frequency: freq });
        }
    }
}
```

### Phase 3: Search and Scoring

```rust
impl BM25Index {
    pub fn search(&self, query: &str, analyzer: &dyn Analyzer, limit: usize) -> Vec<(RowId, f32)> {
        let query_tokens = analyzer.analyze(query);
        let avgdl = if self.total_docs > 0 {
            self.total_length as f32 / self.total_docs as f32
        } else {
            1.0
        };

        let mut scores: HashMap<RowId, f32> = HashMap::new();

        for term in query_tokens {
            if let Some(postings) = self.inverted_index.get(&term) {
                let n_q = postings.len() as f32; // Number of docs containing the term

                // IDF calculation
                let idf = ((self.total_docs as f32 - n_q + 0.5) / (n_q + 0.5) + 1.0).ln();

                for posting in postings {
                    let tf = posting.frequency as f32;
                    let doc_len = *self.doc_lengths.get(&posting.row_id).unwrap_or(&0) as f32;

                    // BM25 term score
                    let numerator = tf * (self.k1 + 1.0);
                    let denominator = tf + self.k1 * (1.0 - self.b + self.b * (doc_len / avgdl));
                    let term_score = idf * (numerator / denominator);

                    *scores.entry(posting.row_id).or_insert(0.0) += term_score;
                }
            }
        }

        // Sort by score descending and limit
        let mut results: Vec<(RowId, f32)> = scores.into_iter().collect();
        results.sort_by(|a, b| b.1.partial_cmp(&a.1).unwrap_or(std::cmp::Ordering::Equal));
        results.truncate(limit);

        results
    }
}
```

### Phase 4: WAND (Weak AND) Optimization (Future)

For very large collections and long queries, calculating BM25 for every document containing *any* query term is slow. WAND or MaxScore algorithms use upper-bound estimates to quickly skip documents that cannot possibly make it into the top-K results.

## Performance Targets

- **Indexing Latency**: < 1ms per KB of text.
- **Search Latency**: < 10ms for a 3-term query over 1M documents returning top 100.
- **Memory Overhead**: The inverted index should use delta-encoding and variable-byte encoding for posting lists to minimize RAM footprint.
